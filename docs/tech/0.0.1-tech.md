2. 技术目标
   2.1 MVP技术目标
   使用一套Next.js应用覆盖PC、Pad和手机浏览器；
   微信小程序通过原生轻壳和WebView复用H5工作台；
   AI任务关闭页面后继续执行；
   项目可以暂停、恢复和重试；
   用户关键判断必须完整记录；
   关键AI输出必须通过结构化校验；
   资料来源可以关联到成果结论；
   微信支付回调必须安全、幂等；
   文件上传和导出不占用Next.js主进程；
   数据库、AI任务和文件之间保持可恢复的一致性。
   2.2 非目标

Kubernetes集群；
复杂微服务体系；
多Agent自由协作；
企业级知识库；
通用向量数据库；
原生iOS/Android App；
社区系统；

5. 架构原则
   5.1 MySQL是业务事实源

以下状态必须以MySQL为准：

用户身份；
项目状态；
当前步骤；
用户判断；
AI运行状态；
支付状态；
用户权益；
成果版本；
文件导出状态。

Redis只负责：

缓存；
队列；
临时登录码；
分布式锁；
实时事件；
限流。

不能将Redis中的任务状态作为最终业务状态。

5.2 队列只传递引用

队列消息只包含：

{
"agentRunId": "run_01J...",
"projectId": "prj_01J...",
"stepRunId": "step_01J...",
"nodeCode": "research_competitors",
"schemaVersion": 1
}

不能在队列中传递：

完整Prompt；
完整用户文件；
企业敏感数据；
完整项目上下文；
微信登录凭证；
支付信息。
5.3 流程由系统控制

AI模型不能决定：

用户是否已经付费；
是否跳过用户判断；
是否执行支付；
是否删除文件；
是否切换境外模型；
是否完成项目；
是否修改用户最终结论。

这些决策必须由状态机和业务规则控制。

19. Outbox一致性
    19.1问题

如果先写MySQL，再发送Redis任务，可能出现：

MySQL成功；
Redis失败；
项目永远停留在排队状态。
19.2解决方案

在同一个MySQL事务中写入：

agent_runs；
project_step_runs；
outbox_events。

Outbox Dispatcher轮询未发布事件并投递BullMQ。

SELECT *
FROM outbox_events
WHERE status = 'PENDING'
AND available_at <= UTC_TIMESTAMP()
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;

发布成功后更新：

status = PUBLISHED
published_at = 当前时间

发布失败：

attempts + 1
available_at = 下一次重试时间

50. 最终技术结论

逐成AI V0.1.0应采用：

Next.js统一多端体验，微信小程序承接微信生态，MySQL保存业务事实，Redis和BullMQ承担异步调度，Agent Worker执行受控AI任务，COS保存资料与成果，微信支付完成单项目付费闭环。

系统最重要的不是模型数量，而是保证：

每个真实任务可以逐步完成；
用户关键判断不会被AI替代；
AI任务可以暂停、恢复和重试；
每条重要结论尽量有来源；
项目成本、质量和执行过程可以审计；
最终成果能够真正用于工作和交付。
